Output

This page describes the output of a run, in six parts. These are the precompile step, the opening block, the lines of the run, the block of a failed item, the closing block and the dry-run plan. The examples come from small suites. Times and memory depend on the suite and on the machine.

The precompile step

┌ [TEST] precompiling 4 stale caches (8 fresh) with 1 worker, at most 16 at once
└ precompiling the env test/qa for 1 profile: default
⬛ w1 · 12:09:51 · UP   · pid 80184 · env test/qa
🟩 w0 · 12:09:52 · COMP · 1/4 · direct · "Helpers"   · v0.2.0 · PASS ·  0.2s
🟩 w1 · 12:09:52 · COMP · 2/4 · direct · "QaTools"   · v1.0.0 · PASS ·  0.2s · maxrss 0.2 GiB · env test/qa
🟩 w1 · 12:09:52 · COMP · 3/4 · direct · "MyPackage" · v0.1.0 · PASS ·  0.2s · maxrss 0.2 GiB · env test/qa
⬛ w1 · 12:09:52 · EXIT · pid 80184 · 2 compiled · 0.9s
┌ [TEST] precompiled 4 stale caches: 3 compiled, 1 reused (8 fresh) in 0.9s
│ w0 · 1 compiled, 1 reused (8 fresh) · env test
└ w1 · 2 compiled · env test/qa

Before the workers start, the run compiles what they will load. Precompilation tells what it compiles and why. When every cache is fresh, the step prints nothing. Otherwise it starts with a block. The first line counts the stale caches, which the step compiles, and the caches that are fresh already. It also gives the number of helper processes, and how many compiles run at the same time. The other lines name the environments, the profiles and the setups.

The lines of the step have the shape of the lines of the run, with a square for a mark:

MarkMeaning
⬛A helper process starts (UP) or ends (EXIT).
🟩A compile built a cache (PASS).
🟨A compile made no cache (SKIP). The module cannot be precompiled, or a package that it loads failed.
🟥A compile failed (FAIL). Its output follows in a block, as for a failed item.

The coordinator compiles for its own environment, as w0. Each other environment gets a helper process, w1, w2 and so on. The helpers start with the step, and each one ends when the compiles of its environment are done. The UP line of a helper names the profiles, the environment and the Julia flags of its compiles. On the line of a helper, maxrss is the most memory that one of its compiles held. A stale cache that another compile builds first is reused. It takes its position and prints no line, so the positions of the printed lines can skip a number.

A COMP line gives the position of the compile among the stale caches, the kind of the module, the package and its version, the outcome and the time. The kind is one of these:

  • direct: a project file of a tested package names the package. For an extension, a project file names the package of the extension.
  • indirect: no project file of a tested package names it. It compiles because another package loads it.
  • testsetup: a setup of a tested package.

The column of the kind is as wide as the longest kind on the lines of the step. In a combined run, a COMP line has one more column after its position, where the line of an item has its package. This column names the tested packages that need the compile. It gives the first one by name and the number of the others, as in Alpha +1:

🟩 w0 · 10:58:23 · COMP · 3/7 · Alpha +1 · indirect · "Dep2"    · v0.1.0 · PASS ·  0.4s
🟩 w0 · 10:58:24 · COMP · 4/7 · Alpha +1 · direct   · "Dep1"    · v0.1.0 · PASS ·  0.6s
🟩 w0 · 10:58:24 · COMP · 5/7 · Beta     · direct   · "Helper"  · v0.1.0 · PASS ·  0.6s

The block at the end splits the stale caches into those compiled, those reused, those failed and those skipped, and gives the fresh caches. When the step had helpers, the block has a line for each worker, with the caches of the environments that it covered. The coordinator also covers each environment that needed no helper. The lines add up to the first line. The EXIT line of a helper gives the same counts as its line here.

While the step runs, the progress line has a white square. It counts the stale caches that are done, all stale caches and the failed compiles, in place of the items. Its workers are the helper processes of the step, and a step without a helper shows no workers. The line also names the oldest compile that runs. In other output, when no compile ends for monitor_interval seconds, the run names the compiles that still run.

The opening block

┌ [TEST] v0.1.0 · julia 1.13.3 · 6 test items in 2 files · seed 0x522fb3b30334cd75 · 2 workers · threads 2,1
│ env: /var/folders/…/jl_7AEUWb/Project.toml
│ machine: 18 CPU threads · 64.0 GiB memory, 21.3 GiB available
└ startup: scan 0.0s · plan 0.1s · setup 1.2s

The first line gives the versions of Runtests and Julia, the number of selected items and files, the git revision (in a checkout), the seed (plus per-item seed counts when replaying failures), the number of workers and their threads, and any non-default Julia flags (for example --check-bounds=yes -O1).

Inside the block, conditional lines report what applies to the run:

  • selection (for example tags = [:fast], or a group with its tags and what asked for it),
  • packages (in a combined run), profile details, and env dir(s),
  • set by the environment (environment variables overriding defaults or TestItems.toml),
  • coverage (and its source),
  • env (path of the test environment), machine (CPU threads and available/total memory, respecting container limits), and startup (scan, plan, and setup timings).

The lines of the run

Workers, items and the run itself each print lines of one shape:

⚪ w0 · 14:52:16 · INFO · 0/6 · 0 failed · 0/2 workers · tree mem 920M (max 920M) · child max 449M · mem 82% · cpu  5.5/18 · testing 0s
⚫ w1 · 14:52:16 · UP   · pid 35898 · threads 2,1
🔵 w1 · 14:52:16 · RUN  · 1/6 · "slow thing" · at test/sub/b_test.jl:9
🟢 w1 · 14:52:16 · DONE · 1/6 · "slow thing" · PASS ·  0.0s (94% compile) · tree max 0.3 GiB
⚫ w1 · 14:52:16 · EXIT · pid 35898 · 3 items · 0.3s

Each line starts with a mark, the worker and the time. The worker is w1, w2 and so on, and w0 is the coordinator. The marks have these meanings:

MarkMeaning
⚫A worker starts (UP) or ends (EXIT), a timeout ends it (KILL), it dies (LOST), or the test_end of a profile did not complete cleanly (HOOK).
🔵An item starts (RUN).
🟢An item passed.
🔴An item failed, errored or timed out.
🟡An item was skipped or was never reached.
⚪The progress line of the run (INFO).

An UP line gives the process ID and the threads of the worker. It also says sandbox for the process of a sandboxed item, and gives the Julia flags of its profile. When an item of the run uses a profile other than default, the line names the profile of every worker. In a combined run, the line names the profile with its package, for example profile default of B. There, only the default profile of the first package has no name on the line. That package is the workspace root when the root has tests. When the run uses an environment directory, the line names the environment of the worker.

A RUN line gives the item's start order in the run (1/N, 2/N, …; retries keep the item's number), its name and its location. A DONE line repeats that number with the outcome, the time, the fraction of the time that was compilation, and memory. tree max is the most memory that the worker and the processes it started held together while the item ran. The run samples it five times a second, so a shorter item gets the memory at the last sample. maxrss is given in its place with monitor = false, or for an item that runs in the process of the run: it is the most memory that the process held since it started. On a timeout, Runtests probes the worker process tree's CPU usage briefly (~0.15 s) before signalling it and appends either worker was idle (likely blocked or deadlocked) (< 5% CPU) or worker was active (<N>% CPU; slow or looping) (>= 5% CPU) to both the KILL line and the failed-item block. The outcome is the result of the body of the item. A HOOK line after it names the test_end of a profile that failed, errored or timed out, with the item, the attempt and the cause. The details go in the log of the attempt. The outcome of the item does not change.

The progress line

On a terminal, the progress line stays at the bottom, and the run draws it again as it goes. In other output, the run prints it at these times:

  • every monitor_interval seconds (skipped if another progress line printed within min(5, monitor_interval) seconds, so routine lines do not land seconds apart),
  • after every 10 finished items, but no sooner than 5 seconds after the last progress line,
  • on any stage transition (setup, testing, reporting),
  • immediately (bypassing the 5-second gap) on upward crossings of high-memory marks (90%, 95%, 96%, 97%, 98%, 99%, each with a 30-second cooldown) or upward crossings of 100% machine CPU saturation (30-second cooldown).

The progress line gives these values:

  • the finished items and the selected items,
  • the number of failed items,
  • the live workers and total worker slots,
  • the memory of the processes of the run, and of the largest of them,
  • the memory and CPU use of the machine. The CPU use is the one-minute load average over the number of CPU threads, for example cpu 5.5/18. A load above the number of threads means that threads wait for a CPU. Windows has no load average. There, the CPU use is the percentage of the CPU time of the machine that was busy in the last 10 seconds, for example cpu 73%.
  • the stage of the run and its time,
  • the active work suffix (when applicable): the oldest running item, collecting artifacts of …, or precompiling ….

While the precompile step runs, the first two values count the stale caches in place of the items, and the workers are the helper processes of the step. Before the tests start, the line names no test workers.

The block of a failed item

An item that did not pass gets a block with its results, right after its DONE line:

🔴 w1 · 12:55:14 · DONE · 1/1 · "fails" · FAIL ·  0.0s (92% compile) · tree max 0.3 GiB
┌ [1/1] FAIL "fails"
│ Test Failed at test/faults_test.jl:6
│   Expression: 1 == 2
│ [ No captured logs
└ @ test/faults_test.jl:5 on worker 1

The block holds the failed tests, the output of the item under Captured logs, and the path of the files that the item kept. The last line gives the location of the item and the worker. The run prints the block as one piece, so the output of another worker never lands inside it. Under logs = :quiet, the block omits item output; read the saved logs afterwards with Runtests.logs.

The closing block

┌ [TEST] ran 6 test items in 2.1s on 2 workers, all passed
│ setup   · 1.1s · tree max  445M · child max  445M · coordinator
│ testing · 0.9s · tree max  1.0G · child max  460M · coordinator + 2 workers · 85% compile
│ (summed resident sizes over-count pages the processes share)
│ machine · 52.9G of 64.0G in use at peak
│ cpu · 8% of 18 threads for this run's processes, 24% for the whole machine (averages over the run)
└ run state: ~/.julia/runtests/runs/MyPackage-8db4f545/1790247276123456-96211.rundata

The first line gives the number of items, the time, the workers and the outcome. Then comes one line for each stage of the run, with its time and memory:

  • tree max is the peak of the summed memory of every process that the run owns. These are the coordinator, the workers, and the processes that they start, for example Pkg or a process that a test starts.
  • child max is the largest single process.
  • The list after it says which processes the peak covers, for example coordinator + 8 workers + 3 spawned.

The cpu line gives two averages over the run, each a fraction of the CPU threads of the machine. The first is the use by the processes of the run. The second is the use by the whole machine. The difference shows how much CPU time other programs used. On Windows, only the use by the whole machine is given, because Windows keeps no total for the children of a process.

The block ends with these lines, when they apply:

  • coverage, with the fraction of lines that ran,
  • run state, the directory of the run, which holds the run state and the logs,
  • in a combined run, one line for each package in place of run state, with the items of the package, those that did not pass, and the directory of its run,
  • copied to, the directory that RUNTESTS_ARTIFACT_DIR named,
  • the evidence that failed attempts kept,
  • run the failing items again, with the command to type, when items failed.

After the block, Test prints its usual summary.

The plan of a dry run

┌ [TEST] dry run · v0.1.0 · julia 1.13.3 · 6 test items in 2 files · 2 workers · threads 2,1
│ startup: scan 0.0s
│ setups: `BasicSetup`
│ timeout: 1800s · retries: 0 · failfast: false · logs: issues · memory_threshold: 0.9
│ estimated work: w1 0.048s · w2 0.066s
└ order and workers: predicted from the recorded durations, an item without one counting as a typical one

  # · worker · test item    · at                   ·  est · tags       · why here      · details
  1 ·     w1 · "slow thing" · test/sub/b_test.jl:9 · 0.0s · slow       · [order] first · timeout 120s
  2 ·     w2 · "chain one"  · test/sub/b_test.jl:1 · 0.0s ·            ·               · throttle `seq`, 1 at a time
  3 ·     w1 · "add works"  · test/a_test.jl:1     · 0.0s · fast
  4 ·     w2 · "chain two"  · test/sub/b_test.jl:5 · 0.0s ·            ·               · throttle `seq`, 1 at a time
  5 ·     w2 · "uses setup" · test/a_test.jl:11    · 0.0s ·            ·               · setup `BasicSetup`
  6 ·     w1 · "mul works"  · test/a_test.jl:6     · 0.0s · fast, math

The table lists the items in the expected order of the run (or the exact recorded per-worker order under replay, where the header block also prints a replay: diff against the current checkout). Each row also gives the worker that is expected to run the item. The estimated work line gives the time that each worker is expected to be busy, from the recorded durations. Without recorded durations, the plan treats all items as equal, and the block has no estimated work line and no est column. The columns have these meanings:

ColumnMeaning
#The position in the plan.
workerThe worker that is expected to run the item.
packageThe package name (shown in combined runtests_mono dry runs).
test itemThe name, or a unique prefix of a long name.
atThe file and the line of the item.
estThe newest recorded duration, in seconds with one decimal. The column shows when earlier runs recorded durations.
tagsThe tags of the item.
why hereThe rule that placed the item, when the rule is not file order.
detailsThe keywords and setups of the item. For an item of a throttle, its limit (and (warmup) when enabled), for example $throttle `gpu`, 2 at a time$.

The output of chores

Runtests.chores() prints one block, with a line for each step. A step that takes longer than 3 seconds shows its duration on its line. Maintain the suite shows an example.

Runtests.chores_mono() prints one block for all packages of a monorepo, with paths from the workspace root. The block also shows the groups of workers. Run the suites of a monorepo describes it.
